# Comment

The user clicked an element in the preview with **Comment** (`C`), wrote a comment, picked an impeccable command (or none) and sent it to the chat. Your job: **this one comment**, on that element, with that command. Nothing else: no other comments, no new screens, no spec changes.

**Important:** Ask every question with the structured question tool (`AskUserQuestion` in Claude Code, `question` in the Design OS chat), never as plain prose: 2–4 options, your recommendation first with the suffix `(Recommended)`, up to 4 independent questions per call, no own "Other" option, short labels.

## Step 1: Read the comment

The message starts with a fenced `design-comment` block:

```design-comment
comment: 3
page: wiki/comments/account.md
target: screen-design            # or: shell
section: account                 # screen designs only
screen: Login                    # screen designs only
command: /impeccable polish  # Improve: edits the source      (or: (none)  # a plain request)
text: |
  Make the sign-in the unmistakable primary action
element: <Button> in LoginForm
anchor: `src/ui/button.tsx:30:10` #0 @ 33.1%,45.8%
call: src/sections/account/components/LoginForm.tsx:40:9  # where the component around the element is used
component: AppShell › Login › LoginForm › Button
classes: "inline-flex … bg-teal-600 …"
html: |
  <button …>Sign in</button>
```

- `anchor` is the element the pin sits on: its source location, which of the elements with that location (`#0`), and the point in its box.
- `call` (optional) is the call site of the component around it. A comment on a primitive from `src/ui/` is about **this usage** unless the text says otherwise: change the props and `className` at `call`, not the primitive.
- The comment itself is the entry `### #<comment> · <command> · <status>` under `## <screen>` on `page`. Read it there too: the user may have edited it after sending.

## Step 2: Load the context

Run these once:

1. `npm run -s impeccable:context`. It links `product/design-system/DESIGN.md` and `wiki/product/PRODUCT.md` to `.agents/context/`, where impeccable reads them. If it reports `PRODUCT.md: missing`, say so in one line and offer `/design-os:wiki-ingest --product` afterwards; continue without it (impeccable proceeds on the incumbent implementation for a scoped change).
2. `npm run -s techstack`. Primitives come from `src/ui/` only, never from `@/components/*`; no new dependency.
3. The `designos-context` skill: `npm run context -- <section-id> --screen <screen>`; for the shell read `product/shell/spec.md`. The section spec is binding.
4. `wiki/design-changes/<section-id>.md` (shell: `shell.md`), if it exists: earlier changes to the same element.

## Step 3: Run the impeccable command

Load the impeccable skill (`.claude/skills/impeccable/SKILL.md`; in the Design OS chat the `impeccable` skill) and follow the reference of the command, with **the element as the target**: pass `--target <file of the anchor or call>` to `impeccable context`. The comment text is the brief.

Design OS rules come first where impeccable would do otherwise:

- **Never** run `init`, `document`, `shape`, `craft`, `live`, `generate`, `hooks` or `pin`. Product truth is `wiki/product/PRODUCT.md` (changed by `/design-os:wiki-ingest --product`), the visual system is `product/design-system/DESIGN.md` (generated by `npm run tokens:build`). Never write either file, also not through `.agents/context/`.
- **Scope is the commented element.** Widen it (the whole component, every usage of a primitive, the whole screen) only after asking. Ask 1–3 questions in one call when the comment leaves the scope or a token choice open, or when it conflicts with the spec, a flow or a persona (show the conflict, the user decides).
- Code-led, never image comps (`.impeccable/config.json` records `buildPath: code`).
- **Check commands** (`critique`, `audit`) change **no file**. Also run `.claude/skills/impeccable/scripts/impeccable detect --json <file>`. Report the findings in the chat, ordered by impact, and write them under the comment (Step 4).
- **Improve and Maintain commands** (`polish`, `layout`, `typeset`, `colorize`, `bolder`, `quieter`, `distill`, `clarify`, `adapt`, `animate`, `delight`, `onboard`, `harden`, `optimize`, `extract`) edit the source:
  - token classes from DESIGN.md ("Token classes" in agents.md), with a `token:` comment, `dark:` variants and responsive prefixes;
  - primitives only from `src/ui/`; a new reusable piece goes to `src/ui/` (`extract` does exactly that);
  - props-based components, no data imports, no navigation in section screens;
  - afterwards run `npm run -s ui:check` and `impeccable detect --json <changed files>`, and fix what they report.
- **No command** (`command: (none)`): treat the text as a Live Edit request on the element (`.claude/commands/design-os/live-edit.md`, Steps 2–3).

Vite HMR updates the preview as soon as a file is saved. Tell the user in one or two sentences what changed (file:line) and ask with the question tool whether it fits. Repeat for adjustments.

## Step 4: Close the comment

Edit the entry on `page`. Change only that entry:

1. The heading's status: `### #3 · polish · sent` → `### #3 · polish · resolved`.
2. Below the quote, add:
   - Improve and Maintain: `**Resolved:** <YYYY-MM-DD> — <what changed>, \`<file>:<line>\``
   - Check: `**Findings:** <YYYY-MM-DD>` and a list, most important first; `**Resolved:**` only once the user is done with them (they may become new comments).
3. Keep the number, the anchor and the user's text as they are; set `updated:` in the frontmatter.

Then, for a change to the source, record it like Live Edit Step 4 (capture with `designos_step: comment:<section-id>/<screen>#<number>`, ingest into `wiki/design-changes/<section-id>.md`) and link the comment page: `[[comments/<section-id>]]`.

Print at the end:

```
Comment #<n> (<command>): resolved
Changed: <file:line>, <summary>            (Check: Findings: <count>)
Recorded: wiki/design-changes/<page>.md
```
